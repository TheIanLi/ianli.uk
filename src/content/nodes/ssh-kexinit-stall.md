SSH 能连上端口，握手却卡在第一步，最后报超时。加一个参数，指定用 `curve25519-sha256` 做密钥交换，马上就能登进去。Claude 当时的解释是，默认的后量子算法包太大，在我这边的路上被丢了。这个解释我现在不太信，原因写在后面。

这个坑不是我踩的，是 Claude Code 帮我搭线路的时候碰上的，我没参与排查。

## 现象

9 月 21 日晚上，我让 Claude Code 把 AWS 新加坡那台机器接到美西落地后面（这条线的来龙去脉在 [VPS](/n/vps/) 那篇里）。它要在新加坡和美西两台机器上改配置，第一步是登上去把配置备份一份。

23 点 16 分，两台都备份成功了。两分钟后它再登新加坡，就登不上了：

```
Connection to ... port 22 timed out
```

它隔 5 秒重试，连着三次都一样。美西那台一直是好的。

## 怎么查的

先看是不是机器挂了。它直接去连新加坡的 22 端口，能连上。代理用的那个端口也是通的。ping 不通，但 AWS 默认就不回 ping，这条不能说明任何问题。

端口是通的，SSH 却超时，那就是连上以后卡在了中间某一步。它开了 `ssh -vv` 看详细过程：双方互报了版本号，都是 OpenSSH 9.6p1，然后客户端发出 `SSH2_MSG_KEXINIT sent`，就再没有下文了。KEXINIT 是 SSH 握手的第一步，双方在这一步交换自己支持哪些加密算法。

它又看了一眼本机网卡的 MTU（一个包最大能多大），出去的那块网卡是 1400，比常见的 1500 小。

然后它换了个位置测：先登上美西那台，从美西去 SSH 新加坡。这次 KEXINIT 正常走完，日志里能看到双方商量出来的密钥交换算法是 `sntrup761x25519-sha512`。

从美西能登，从我这里不能，所以它判断新加坡的机器没问题，问题出在我这边到新加坡的这段路上。

## Claude 给的解释和修法

`sntrup761x25519` 是 OpenSSH 新版默认的后量子密钥交换算法，比老算法多传一大块数据。Claude 的判断是，这种大包在我这边的路上被丢了，所以握手卡住。修法是指定用老一点、包小一点的算法：

```
ssh -o KexAlgorithms=curve25519-sha256 ...
```

23 点 24 分加上这个参数，第一次就登进去了，之后那一晚的活全靠它干完。它最后跟我说，以后我自己 SSH 新加坡要是也卡住，就是这个原因。

## 我为什么不太信这个解释

写这篇的时候回去翻了记录，有两件事对不上。

第一，卡住之前两分钟，同一台电脑、同一台机器、默认算法，备份是成功的。如果是包太大一定会被丢，那两分钟前也应该登不上。

第二，三天后的 9 月 24 日，我让 Claude Code 去新加坡测延迟。它第一次登录带了这个参数，后面几次没带，也都登上了。

所以更像是那条路在那几分钟里不稳定，换个参数正好赶上它恢复。也可能参数确实有用，只是这毛病时有时无。到底是哪种，没有再查过。当时没抓包，也没在登上去以后立刻用默认算法再试一次，现在已经没法验证了。

这个参数我还留着用。它没坏处，最多就是白加。
